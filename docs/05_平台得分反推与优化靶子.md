## 一、为什么这份数据重要

在此之前我们只能看到**总分 15.3**，不知道分丢在哪 —— 15 个测试点
各丢多少、哪个是重灾区，全是猜的。

现在平台上多出了一列 **「最优用时」**，它就是得分公式里的 `T`：

```
单点得分 = 100 / (1 + log₁.₅(t / T))
总分     = 15 个单点得分的平均值
```

有了 `T`，再用我们自己那次提交的 `用时`（就是 `t`），就能把每个点的
得分**精确算出来**。

## 四、结论：两个性质完全不同的战场

### 战场一 — 测试点 8 / 9 / 10 / 11 / 12 / 13（6 个点，平均 8.3 分）

`t/T` 从 **37.7 倍到 694 倍**。这 6 个点就吃掉了绝大部分失分。

**测试点 13 尤其反常**：

```
T = 1.40 µs    ← 全部 15 个点里【最小】的最优用时
t = 971.53 µs  ← 全部 15 个点里【第二慢】的用时
t/T = 694 倍
```

T 只有 1.4µs 说明**问题规模极小**（基本只剩 kernel 启动开销的量级），
而我们花了将近 1 毫秒。**这一定是某个形状让 kernel 走进了灾难性的慢路径**，
是最值得优先解剖的一个点。

### 战场二 — 测试点 1~7、14、15（9 个点，平均 20.0 分）

`t/T` 是 3.2~13.7 倍。这些点的 **T 只有 1.40~11.86 µs** ——
也就是"几乎只剩 kernel 启动开销"的量级。

⇒ 说明**我们设备端的固定开销本身就比最优实现大 3~14 倍**。
本地实测 `kernel` 段（启动 + 执行 + 同步）是 28~34 µs，
而平台最优只需 1.4 µs —— 差距主要来自**重型的 Matmul 高级 API 的固定开销**
（`REGIST_MATMUL_OBJ` / `SetOrgShape` / `SetTensorA/B` / `SetTail` / `IterateAll`
这一串，以及 `TPipe` + 6 个 `InitBuffer`）。

### 收益估算

| 目标 | 需要的动作 | 预期总分 |
|:---|:---|:---|
| 现状 | — | 15.3 |
| 战场一 6 个点提到 20 分 | 解决"形状相关的灾难性慢路径" | ≈ 20.0 |
| 战场一 + 二都提到 20 分 | 再减掉设备端固定开销 | ≈ 20.0 |
| 全部 15 点提到 25 分 | t/T 压到约 3.2× | 25.0 |

## 五、M 并行（M-parallel）工作总结

### 已完成

把任务单位从「一个核 = 一个 batch」改成「一个核 = 一个 (batch, M块) 单元」：

```cpp
// 原来：B=1 时只有 1 个核在干活
for (b = GetBlockIdx(); b < B; b += coreNum)

// 现在：B=1 且 16 个 M 块 → 16 个核一起跑
for (unit = coreIdx; unit < totalUnits; unit += coreNum) {
    b  = unit / numMBlocks;
    mb = unit - b * numMBlocks;
}
```

每个核把 partial 累进本核的 `partLocal[b]`（UB 内、带 Kahan 补偿），
写进 GM 部分和区，`SyncAll()` 之后按固定顺序归约。

### 实测收益（本地，CANN 9.1.0 + Ascend910）

| 用例 | M块数 | 旧 | 新 | 提速 |
|:---|---:|---:|---:|---:|
| case01 | 1 | 82.13 µs | 84.11 µs | 1.00× |
| case13 | 2 | 90.51 µs | 83.03 µs | 1.09× |
| case14 | 4 | 113.49 µs | 87.05 µs | 1.30× |
| case21 | 8 | 160.07 µs | 98.10 µs | 1.63× |
| case23 | 8 | 138.01 µs | 87.36 µs | 1.58× |
| **case17** | **16** | **605.96 µs** | **146.10 µs** | **4.15×** |

**提速与 M 块数严格单调** —— 这是"按 (batch, M块) 切分"生效的直接证据。

### 踩过并修掉的坑

**1. false sharing（跨核部分和区）**

原来布局是 `partGm[b * 核数 + 核号]`。B 只有 8 个 float = 32 字节，
**一条 cache line 里塞着十几个核的数据**，多核并发写会互相冲掉。

症状：8 个输出里偶发 1 个变成 0；核数越多越严重（20 核时耗时暴涨到 100 ms）。

修法：布局改成 `partGm[核号 * kPartStride + b]`，`kPartStride = 128`
（512B ≥ 4 条典型 128B cache line），每核独占一整段；同时把标量 `SetValue`
改成 DMA `DataCopyPad`。

**教训：跨核共享的 GM 缓冲，只要多个核会写相邻地址，就必须按 cache line 拉开。**

**2. 两个假设尚未分离（未解决）**

修掉 false sharing 后，下面这条规律**依然成立**，且没有任何例外：

| 每核分到的单元数 | 结果 |
|:---|:---|
| **恰好 1 个** | ✅ 全部正确（7 个用例） |
| **多于 1 个** | ❌ 全部出错（case18: 80 ms + 7/8 错；case19: 94 ms + 全 0） |

两个候选解释，尚未做实验区分：

- **H1**：每核处理多个单元本身有问题
- **H2**：核数正好撞上物理上限（20）时 `SyncAll` 有问题

**区分实验已设计好但未执行**：让 case18 用 16 个核跑。
单元/核 = 64/16 = 4（满足 H1），但 16 < 20（不满足 H2）。
坏了 ⇒ H1；好了 ⇒ H2。为此在 host 侧留了诊断开关 `BMMS_MAX_CORES=<n>`。

### 当前采用的保守策略

`kernel_mpar.asc` 做成了**混合版**：

```
useMpar = (B * numMBlocks < availableCoreNum)      // 严格小于，留一个核余量
真 → blockNum = B*numMBlocks，每核恰好 1 个单元 → M 并行路径（已验证）
假 → blockNum = min(B, availableCoreNum)        → 原版路径（逐字未改）
```

判据由 host 算好写进 `BmmsTiling.useMpar`，所有核读到同一个值，
不会出现"部分核进 if、部分核进 else"导致 `SyncAll` 缺席死锁。

**已用脚本逐字比对确认**：`kernel_cachefix.asc` 的 batch 循环体 12621 字符，
与 `kernel_mpar.asc` 中 else 分支里的同一段**完全相同** ——
退回的那条路径与平台 15/15 的版本是一模一样的代码。

## 六、提交被拒记录

### 第一次：kernel_mpar_clean.asc → 「代码中有不合规的内容」

平台报的是**内容扫描**，不是编译错误。

对比之前**被接受**的 `kernel_cachefix.asc`，本版新增的东西只有两类：

| 新增内容 | 判断 |
|:---|:---|
| `getenv("BMMS_MAX_CORES")` / `atoll` | 运行时读环境变量 —— 最典型的嫌疑项 |
| `printf(...)` × 2 | 设备/宿主代码里的调试输出 |

`make_submit_kernel.py` 把这两类整体删掉，再复用 `strip_comments.py` 的
状态机剥掉注释，得到**纯计算代码**（无 I/O、无环境变量、无字符串字面量、
无中文字符）：`kernel_mpar_submit.asc`（497 行 / 19913 字符）。

### 第二次：kernel_mpar_submit.asc → 仍然 Compile Error（15/15）

**关键事实：这份代码在本地 CANN 9.1.0 下编译是通过的。**

⇒ 说明代码本身合法，**平台的 CANN 版本更老，不支持其中某个 API**。

对照排查：

| 用到的 API | 在被接受的 `kernel_cachefix` 里出现过吗 |
|:---|:---|
| `DataCacheCleanAndInvalid<ENTIRE_DATA_CACHE>` | ✅ 出现过 |
| `DataCopyPad(GlobalTensor, LocalTensor, DataCopyExtParams)` | ✅ 出现过 |
| `AllocEventID` / `SetFlag` / `WaitFlag` | ✅ 出现过 |
| **`AscendC::SyncAll()`** | ❌ **从未用过 —— 第一嫌疑** |

**下一步**：拿到平台的确切编译报错。如果确认是 `SyncAll` 的写法问题，
需要考虑替代方案（例如按 2D grid 拆成两次归约、或改用其他跨核同步原语）。
