## 为什么现在做这个

平台提交385438证明第77轮只命中测试点1；用户明确要求不能放弃测试点8~12的毫秒级
用例。它们当前合计仅约43.8分，若接近最优，理论上足以给最终均分增加约30分，是40+
目标不可缺少的部分。

现有 `bmms_main` 只按 B 分核：当 B=1、M很大时仅1核串行遍历所有 mBlock，其他19核
闲置。第77轮已经在独立 N=1 通路上证明，改变并行维度可以把本地大 M 用例从约
1190µs降到5.98µs。

## 本轮改动

- 主 kernel 的任务空间从 `B` 改为 `B*numMBlocks`。
- 每个 task 唯一对应 `(batch, mBlock)`，复用原先已验证的 Matmul、N归约与Kahan逻辑。
- 每个 task 得到一个 mBlock partial sum，末尾只执行一次 FP32 atomic add 到 `y[b]`。
- host 对主通路先在同一 stream 用 `aclrtMemsetAsync` 清零完整 y。
- blockNum 改为 `min(B*numMBlocks, availableCoreNum)`；每核 scratch 仍独立。
- `bmms_dot_n1` 与 `bmms_vec` 的分发和算法不变。

风险：M方向求和从严格顺序变为跨核原子顺序，可能带来容差边缘误差；平台已证明原子
与跨 launch cache 机制本身安全，但主通路覆盖 shape 更多，因此必须重新跑完整验证。

# 📌 第 73 轮：🔑 **解开了 1/15 与 TLE 之谜 —— 是概率性卡死**（重要）

## 关键线索（用户提供）

**第 68 轮的探针版（`kBaseM=128` + `mbRows` + `kVecPathEnabled=false`）被提交了两次：**

| 次 | 结果 |
|---|---|
| 第一次 | **Time Limit Exceeded** |
| 第二次 | **全 Wrong Answer + `用时` 整列 `-`** |

**同一份代码，两种结果。**

## 结论：这不是"算错了"，是**概率性卡死**

- **TLE** = 卡到超时上限
- **全 Wrong + `用时 -`** = 内核没干完活
   （STATUS.md 早有定义：`用时 -` ≡「这个测试点的 kernel 几乎没干活」）

**两者是同一种病的两种表现**，区别只在卡住的时机相对于平台超时的位置。

**本项目历史上踩过一模一样的坑** —— `kernel.asc` 第 388~390 行的注释原文：

> 事件 ID 只有 0~7，硬编码的 EVENT_ID0/1 会与 Matmul 占用的 ID 冲突 →
> WaitFlag 等不到标志位 → **卡死（现象："全 Wrong Answer + 用时整列 -"，约 1/3 概率命中）**

**"约 1/3 概率"** —— 这就是同一份代码两次不同结论的来源。

## 所以「是不是平台的问题」？

**不是平台随机判分，是内核有概率性卡死，平台忠实报告了它的两种面貌。**

| 版本 | 提交次数 | 结果 |
|---|---|---|
| `kernel_cachefix.asc`（kBaseM=64） | **4** | **4/4 都是 15/15** |
| `kBaseM=128 + mbRows` | 2 | 2/2 失败（形态不同） |

⇒ **平台的判定是稳定的；不稳定的那个是我们的内核。**

## 两条最可能的机制（都来自代码本身）

### ① UB 占用从 35% 跳到 68%（主要怀疑）

```cpp
pipe.InitBuffer(cBuf, baseM * kPitch * sizeof(float));   // kernel.asc:395
```

| 版本 | cBuf | +maxBuf+redBuf+yBuf | 占 910B3 的 192KB |
|---|---|---|---|
| 已知 15/15（`kBaseM=64`） | 64KB | **≈66.6KB** | **35%** |
| `kBaseM=128` | 128KB | **≈130KB** | **68%** |

**边界性的资源压力完全可以表现为"偶发"失败，而不是每次必挂。**

### ② 运行期 `SetShape(mbRows=16, …)` 的退化 tiling

`mbRows = alignUp16(min(M,128))` ⇒ 对 **M<16** 的形状传 `singleCoreM=16`，
配上 `SetOrgShape(M=1,…)` 是退化组合。
**而本地所有 M<16 的形状（case0/8/11）都被向量通路守卫分流走了，
matmul 从来没拿到过 `16` 这个值 ⇒ 本地覆盖为零。**

## ★★ 永久封存（不是"以后再试"，是**不能再试**）

> **`kBaseM=128` 与 `mbRows` 自适应这两个改动，永久放弃。**

理由不是"收益只有 +0.5 分"，而是：

> **这份代码会"偶尔成功"。** 如果哪次提交侥幸 15/15，我们就会把它当成好版本发出去 ——
> **而它是个随时会炸的地雷。这比稳定失败危险得多。**

**⇒ 只要不能复现平台的调用形态（`dev/main_dev.asc` 不允许改），
任何"偶发失败"的改动都无法被本地验证，因此一律不能进提交物。**

## 这条教训值得单独记住

**判据不只是"通过数"**：
- 稳定失败（每次都挂）⇒ 可以定位、可以修
- **偶发失败（时好时坏）⇒ 必须整体放弃**，因为无法验证，且会伪装成成功

历史上第 7、12/13、18/19 轮把"卡死"误判成"改动有害"，白白回退了正确的改动；
本轮反过来 —— 差点把"偶发卡死"误判成"可修的 bug"。**两个方向都吃过亏。**

**但 M 小的用例反而变慢** —— `SetShape(128, N, K)` 让 matmul **按 128 行整块算**，
而 M 只有 16/17 ⇒ **白算 8 倍飞行行**。

⇒ 大 M 要"块大"（少几次调用），小 M 要"块小"（别算飞行行）。**二选一是错的，必须自适应。**

## 本轮改动（一个概念，五处配套）

```cpp
// host
const int64_t mbRowsRaw = (M < kBaseM) ? M : kBaseM;
const int64_t mbRows    = ((mbRowsRaw + 15) / 16) * 16;   // matmul 的 singleCoreM 必须是 16 的倍数
const int64_t numMBlocks = (M + mbRows - 1) / mbRows;
tilingApi.SetShape(mbRows, N, K);      // 原 kBaseM
tiling.mbRows = mbRows;                // 新增字段，传给 kernel
// kernel
const int64_t mbRows = t->mbRows;
const int64_t tm0 = mb * mbRows;                              // 原 mb * baseM
const int32_t tmCnt = min(M - tm0, mbRows);                   // 原 baseM
const int32_t reduceRows = (tmCnt + 7) / 8 * 8;               // ★ 归约上界由 baseM 改为 alignUp8(tmCnt)
for (int32_t g = 0; g < reduceRows; g += kRowGroup)           // 原 0..baseM：M=16 时白扫 16 组
```

**UB 尺寸一律仍按编译期的 `kBaseM` 开**（`cBuf`、`runningMax`、scratch），只有"推进/循环上界"用运行期的 `mbRows`。
**两条 tiling 路径（正常 + fallback）都改成 mbRows，必须一致，否则结果错。**

|---|---|---|---|---|
| 13 | 255 | 128 | 2 | **≈68µs**（保住第 66 轮的收益） |

## 根因

第 61 轮我把 **x2 整块连续搬进 UB**（行距 = N）。**N 不是 16 的倍数时，`bH[k*N]` / `bF[k*N]` 的起始地址不是 32B 对齐**，
而 UB 上的 `Cast` / `Axpy` 要求地址 32B 对齐 ⇒ 结果错乱。

## 修法

**x2 也逐行搬**，行距补齐到 16 的倍数：

```cpp
const int32_t bRow = (N + 15) & ~15;          // 行距（16 元素 → fp16 32B / fp32 64B）
pipe.InitBuffer(bHBuf, bEl * sizeof(T));      // bEl = K * bRow
pipe.InitBuffer(bFBuf, bEl * sizeof(float));
for (k...) DataCopyPad(bH[k*bRow], bGm[k*N], {1, N*sizeof(T)}, pad 到 bRow);
for (k...) Cast(bF[k*bRow], bH[k*bRow], CAST_NONE, N);
for (k...) Axpy(acc, bF[k*bRow], s, N);
```

**代价**：x2 的搬运由 1 次变成 K 次（K ≤ 512，本轮守卫下实际很小）。

**UB 占用复核**（守卫 `M*K≤2048, N≤256, K≤512, K*N≤8192` 之下）：
`bF ≤ 64KB + bH ≤ 32KB + aL ≤ 4KB + acc ≈ 1.3KB ≈ 101KB` < 192KB ✅

| aicore time | 65.746 µs | AIC **≈100% 忙 ⇒ 它就是关键路径** |
| **aic_scalar_time** | **61.757 µs** | **93.9%** ← 大头 |
| aic_mac_time | **0.532 µs** | **0.8%** ← 矩阵乘几乎不干活 |
| aic_fixpipe_time | 25.336 µs | 38.5% |
| aic_mte2_time | 9.464 µs | 14.4% |
| aiv_time | 34.731 µs | 只有 53% ⇒ **AIV 有 47% 空闲** |
| aiv_vec_time / aiv_scalar_time | 8.371 / 9.984 µs | — |
| cube_utilization | 4.969 % | — |
| Block Num / Mix Block Num | 1 / 2 | — |

## 结论一：`kBaseM` 假设**被否证**，原因是机制搞错了

`numMBlocks` 4 → 2，时间只动 5%。原因：

> **matmul 内部在 M 方向自己还会按 `baseM` 再切一遍。**
> 我们外层的 m 块怎么切，**它内部的循环次数根本不变** ⇒ 改这个量对 AIC 毫无影响。

（第 53 轮原以为"每块重来一遍 setup"是大头 —— 按 5% 反推，一次 setup 约 2µs，不是瓶颈。）

## 结论二（**价值更高**）：AIV 不是关键路径

`aiv_time` 只有 34.7µs，而 duration 是 66µs ⇒ **AIV 有近一半时间在闲着**。
**这从数据上解释了为什么此前所有"向量侧优化"全部无效** —— 优化一个不忙的单元，当然没用。
**归约、搬运、掩码、repeatTime 这些以后不要再动**（除非 AIV 变成关键路径）。

## 结论三：AIC 花 62µs 干 0.5µs 的活

`aic_mac` 仅 0.53µs（5.2 MFLOP ⇒ 约 9.8 TFLOP/s，cube 利用率 4.97%），
而 `aic_scalar` 61.76µs。**这是"指令流/控制流"型瓶颈，不是算力瓶颈。**

⇒ 顺着"**与块数无关、每次调用一遍、在 AIC 侧**"这三个条件筛，
头号嫌疑锁定为第 44 轮加的 `DataCacheCleanAndInvalid<ENTIRE_DATA_CACHE>`
（全 cache 刷写，**脏行越多越贵** —— 小测试点 t=13~37µs、脏行少，正好对得上）。
**第 54 轮就是去量它。**

## 本轮唯一改动

```cpp
constexpr int32_t kBaseM = 128;   // 原为 64
```

连带**自动**变化（都由这一个常量推导，没有第二处手工改动）：

| 量 | 改前 | 改后 |
|---|---|---|
| `numMBlocks`（M=255 时） | 4 | 2 |

## 为什么选这个改动（判别逻辑）

```cpp
mm.SetTail(tmCnt, N);
mm.IterateAll(cGm);            // ← 每次只算 64×N×K
```

M=255、kBaseM=64 ⇒ **4 遍 setup**，每遍真正算的只有 64×257×40。

> 1. B 矩阵的行距（B 存 `(K,N)` 时，沿 K 跨一步要走 N）

**⇒ `singleCoreN` 可以缩小，但 C 的行距永远是完整 N，scratch 必须保持 `kBaseM × N`。**
**这条路封死。**

## 🔑 判题 golden 的权威实现（第 36 轮取证，`scripts/BatchMatmulMaxSum.py`）

**这是判题 golden 本身**，三条硬事实：

### 1. 形状读法被彻底证实

```python
x1_shape = (B, K, M) if transposeX1 else (B, M, K)
x2_shape = (B, N, K) if transposeX2 else (B, K, N)
```

与我们的 `shape[tx1?2:1]` / `shape[tx1?1:2]` / `shape[tx2?1:2]` **逐项一致** ✓。
第 31 轮"x1 存储读法"与第 24 轮"x2 存储读法"的结论都对了，
"两种读法各自成立、别去统一"这条约定也确认了。

### 2. golden 是 FP64

`astype(np.float64)` → `np.matmul` → `np.max(axis=-1)` → `np.sum(axis=-1)` → `astype(np.float32)`
⇒ 算法三段式与我们完全相同，**但精度是 fp64**。

### 3. 输入是**按用例固定种子**生成的

```python
rng = np.random.default_rng(20260817 + cid)
```

⇒ **输入固定 + kernel 确定性 ⇒ 不存在真正的"抖动"。**
STATUS.md 早期记的"同一份代码通过数会跳"，回头核对基本都发生在**不同代码版本之间**。
**剩余失败是确定性的、可复现的。**

### 定位过程（`dev/sweep.py` 是关键工具）

1. **本地 11 个用例全过、误差 1e-6 量级** ⇒ 判题的失败**不是精度地板**。
   但这 11 个用例 `B ≤ 4` —— `gen_cases.py` 的 `BIG_IDS` 默认把 **B=64** 那个排除了，
   **B 这个维度从来没被覆盖过**。而判题失败的 5/6/7 恰好是 **B = 8/13/16**。
2. **写 `dev/sweep.py` 按 B=8/13/16 + N≤256 做网格扫描** ⇒ 立刻复现：
   `B=8 M=16 N=65 K=32` → **错 4/8，max|diff|=73，max_rel=1.0**（一半输出是 0）。
3. **加 kernel 内 printf 打印每个 block 的 `total`**：
   **8 个 batch 算出的值与 FP64 golden 逐位吻合** —— 计算完全正确。
4. **再加 `yWrote` 读回**：8/8 读回也正确。但 host 拷回的 y 里一半是 0。
5. **逐行核对 `dev/main_dev.asc`**（`aclrtMemcpy`/同步/大小）⇒ **驱动没问题**；
   且 `memset(hostY,0)` 在 D2H 之前 ⇒ 文件里的 0 只能来自 `devY`。

⇒ **值停在 aicore 的 cache 里，从未回写到 GM。**
kernel 内的读回命中的是同一个 cache，所以"看起来写成功了"。

### 修法

```cpp
// 1) y 的写出改走 DMA（向量单元产出 → DataCopyPad）
Duplicate(yLocal, total, 1);
AscendC::SetFlag<AscendC::HardEvent::V_MTE3>(evtV2E3);
AscendC::WaitFlag<AscendC::HardEvent::V_MTE3>(evtV2E3);
DataCopyPad(yGm[b], yLocal, ycp);

// 2) kernel 结束前显式回写 cache —— **这一句才是决定性的**
AscendC::DataCacheCleanAndInvalid<float, AscendC::CacheLine::ENTIRE_DATA_CACHE>(yGm);
```

- `dev/sweep.py` 240 组合**全部 ok**（修复前"基本全是 fail"）
- `run_case.sh all` **11 通过 / 0 失败**，误差回到 `1e-6` 量级
- 说明：**只加 DMA 不够**（第一次尝试失败），**`DataCacheCleanAndInvalid` 才是关键**

## 🎯 第 42 轮：M 方向拆 8 行一组，`repeatTime` 64 → 8（已完成）

### 动机

- 官方样例用的是 **`repeat = 8`**，我们用的是 **64**。
- 第 40 轮只把 `srcRepStride` 挪了 8 个 block，就从 13/15 崩到 1/15
  ⇒ **这个 multi-repeat 机制对参数极端敏感**，而 64 是官方样例的 8 倍。

### 改法

```cpp
constexpr int32_t kRowGroup = 8;
for (int32_t g = 0; g < baseM; g += kRowGroup)
    for (int32_t c = 0; c < colChunks; ++c) {
        WholeReduceMax<float>(redTmp, cLocal[g*kPitch + c*kF32PerRepeat],
                              kF32PerRepeat, kRowGroup, 1, 1, tileStrideBlocks);
        Max(runningMax[g*kReduceStride], runningMax[g*kReduceStride],
            redTmp, kRowGroup * kReduceStride);
    }
```

结果落在 `redTmp[0..15]`，对应 `runningMax` 的 `[g*2, g*2+16)`（value/index 交错）。

### 代价

调用数由 `colChunks` 变成 `8 × colChunks` —— **只涨 8 倍，基数极小**
（N=8192 时 32 次 vs 4 次），**绝不会 TLE**。与第 41 轮的 ×64 有本质区别。

### 判别

| 结果 | 结论 |
|---|---|
| 5、6、7 清零 | `repeatTime=64` 超限 ⇒ 机制确认，修掉 |
| 无变化 | repeat 次数不是元凶 ⇒ 该假设否证，继续在"单列块"这条线上找 |

> gap 这条路彻底封死，不要再试。**

### 但崩盘同时暴露了真正的病灶

- 传 24 → 1/15；传 32 → 13/15。**差 8 个 block（64 个元素）就从"几乎全对"崩到"几乎全错"**

- 而 32 对行距 256 来说**就是精确正确的值**（256×4/32 = 32）⇒ **语义没错、值没错，

- 回看第 38 / 39 轮：两次唯一的差别是**行距**（256 vs 128），

⇒ **收发式（一次调用跨多行）的 `WholeReduceMax` 在我们的用法下不可靠，
而且不是参数选择能修好的。**

### 改法：单列块路径彻底不用 `srcRepStride`

```cpp
if (N <= kTileN) {

    for (int32_t i = 0; i < tmCnt; ++i)
        for (int32_t c = 0; c < colChunks; ++c) {
            WholeReduceMax<float>(redTmp, cLocal[i*kPitch + c*kF32PerRepeat],
                                  kF32PerRepeat, 1, 1, 1, 1);
            Max(runningMax[i*kReduceStride], runningMax[i*kReduceStride], redTmp, 1);
        }
} else {
    ... 保持原收发式（8~15 目前通过，调用数也不会爆）
}
```

**为什么只在单列块启用**：逐行的调用数是 `tmCnt × colChunks`（×64）。

## 🎯 第 40 轮：`srcRepStride` 改用「间隔(gap)」语义（已完成，**已否证**）

### 第 39 轮的结果：`{5, 6, 7}` —— **并集**

| 轮次 | 列块宽 W | 行距 P | 失败集合 |
|---|---|---|---|
| 35 | 256 | 256 | `{5, 7}` |
| 36 / 37 | 128 | 128 | `{5, 6}` |
| 38 | 256 | 256 | `{5, 7}` |
| **39** | **128** | **256** | **`{5, 6, 7}`** |

**两个维度各自独立造成失败** ⇒ 第 39 轮"拿到唯一归因"的设计目标是错的，
**不是一个元凶，而是同一个机制在两种配置下各自读错**。

### 唯一能一次说清全部观测的机制

**前提**：C 的值在所有配置下**完全相同**（matmul 的 tiling 没变，UB 布局变化不影响
它的输出）⇒ 差异**只可能来自归约本身**。

> **若 `srcRepStride` 被理解成「相邻 repeat 之间的间隔(gap)」而不是「绝对跨距(stride)」**，
> 则第 r 个 repeat 读到的不是第 r 行，而是第 r 行**靠后一段**的位置。
> 读到的**仍然是真实的 C 数据**（只是来自别的行）⇒ 得到的"行最大值"是
> **一组被错位取样的真实行最大值** ⇒ 对 M 求和时**有的行被重复计入、有的被漏掉**
> ⇒ 误差**很小**，只在 `|y|` 很小的那个 batch 上越界 ⇒ **恰好 1 个元素**。

**这个机制同时解释全部观测**：

| 观测 | 解释 |
|---|---|
| 随列块宽 W 变 | 错位取样落在哪些行会变 |
| 随行距 P 变 | 错位幅度 = P/8 变 |
| 与掩码无关（第 37/38 轮） | 错位是 repeat 间的地址推进，与 mask 无关 |
| 与 Kahan 无关（第 35 轮） | 误差在求和**之前**就已进入行最大值 |
| 只错 1 个元素 | 只是少数行被重复/漏掉，误差量级很小 |

### 改法（一行）

```cpp
// 改前：绝对跨距
constexpr int32_t tileStrideBlocks = kPitch * sizeof(float) / kBytesPerBlock;              // 32
// 改后：间隔(gap) —— 行距 减去 一次 repeat 的消耗量
constexpr int32_t tileStrideBlocks = (kPitch - kF32PerRepeat) * sizeof(float) / kBytesPerBlock;  // 24
```

### 判别

| 结果 | 结论 |
|---|---|
| 5、6、7 全部清零 | 机制确认，bug 同时被修掉 |
| 失败变多 / 变严重 | 「绝对跨距」成立，该假设否证 ⇒ 改去动 UB 布局（把行距钉成 64，使 repeat 之间天然连续） |

### ⚠️ 第 36 轮的归因缺陷（本轮才看清）

第 36 轮**同时**改了列块宽度和 UB 行距（两者一直绑在同一个 `kTileN` 上），
所以"失败点移动"跟的是**哪个**，从来没有被分开过。这是一个真实的实验设计缺陷。

而唯一随列分解变化的量是 `srcRepStride = 行距/8`，它跟的是**行距**。

### 本轮的拆分

```cpp
constexpr int32_t kTileN = 128;   // 列块宽度 → colChunks / nValid / 循环步长
constexpr int32_t kPitch = 256;   // UB 行距   → srcRepStride = 32
```

`srcRepStride` 停在第 38 轮那一档(32)，列分解换成第 36/37 轮那一档(128)。
于是结果是一个**唯一归因的二分**：

| 结果 | 结论 |
|---|---|
| 失败集合变 `{5, 6}`（跟列块宽度走） | `srcRepStride` 无关 ⇒ 另找方向 |
| 失败集合变 `{5, 7}`（跟行距走） | **`srcRepStride` 就是元凶** ⇒ 下一轮把行距钉成与分解无关的常量 |

### 配套改动（必须同步，否则会读到脏数据）

- `DataCopyPad` 目标地址：`cLocal[i*kTileN]` → `cLocal[i*kPitch]`
- `Duplicate` 填充：区间由 `[nCopy, kTileN)` 扩到 **`[nCopy, kPitch)`**（整行）
- `cBuf` 大小、`tileStrideBlocks` 均按 `kPitch`

⇒ 于是 `[nCopy, kPitch)` 全是 `kNegBig`，满宽掩码在任何情况下都读不到脏数据；
而列块循环只覆盖 `[0, kTileN)`，`[kTileN, kPitch)` 那段不被读。

## 🎯 第 37 轮：归约改满宽掩码（已完成，结果见上）

### 第 36 轮的结果：失败点**移动了**

`kTileN` 256→128 后仍然是 13/15，但失败集合 `{5, 7}` → `{5, 6}`，
各自仍是**恰好 1 个元素**（12.50% / 7.69%）。

**这个"移动"本身就是判决**：

- C 的值由 matmul 决定，与 `kTileN` 无关
- M 方向求和的**求和项也没变**（每个行最大值都相同）
- ⇒ 唯一随分解改变的，就是**"max 是怎么被算出来的"**
- ⇒ **我们算出的 max 并不是真正的 max**，归约里有 bug

### 铁证其实第 17 轮就记下了，只是当时结论下反了

> 第 17 轮：改为满宽拷贝 + 依赖 mask 限宽 → **mask 并不排除范围外元素**，判断错了

"**mask 并不排除范围外元素**"就是直接证据。收窄掩码 `mask = nValid - col0`
是个**任意整数**（44 / 36 / 1 …）。若它被截断到 32B 边界（fp32 即 8 的倍数），
`mask=44` 退化成 40 ⇒ **真实存在的第 40~43 列被整个丢掉** ⇒ 该 batch 的 max 偏小
⇒ 恰好只错 1 个元素；`kTileN` 一变，截断位置就变 ⇒ 换另一个 batch 受害。
**与观测逐条吻合。**

### 改法：不需要再对 mask 语义做任何假设

`[nValid, kTileN)` **已经**全部是 `kNegBig`（`DataCopyPad` 右侧填充 + `Duplicate`
整段刷，两段合起来覆盖满 `kTileN`）。而真实值 `|C| ≤ K ≤ 2^21`，
**永远不可能低于 -3e38** ⇒ **用满宽掩码，让 `kNegBig` 自己去输**。

```cpp
// 改前：mask = min(nValid - col0, 64)   ← 任意整数，会被截断，丢真实列
// 改后：mask = kF32PerRepeat (64)        ← 满宽，只处理真实值或 kNegBig
for (int32_t c = 0; c < colChunks; ++c) {
    const int32_t col0 = c * kF32PerRepeat;
    WholeReduceMax<float>(redTmp, cLocal[col0], kF32PerRepeat, baseM, 1, 1, tileStrideBlocks);
    Max(runningMax, runningMax, redTmp, rowElems);
}
```

**收益**：归约不再依赖掩码语义 —— 不管 mask 是元素个数、位掩码、还是按 8 对齐截断，
结果都一样正确。逻辑也更简单（不再需要按 `nValid` 提前 `break`）。

### ⚠️ 与第 17 轮那次失败的区别（别混淆）

第 17 轮是"满宽**拷贝**"：`blockLen` 取 `kTileN`，从 GM **越读下一行的真实数据**，
并指望 mask 去排除 —— 那是错的。
本次**拷贝长度仍是 `nValid`，GM 侧一个字节都不多读**，越界部分全部由
我们自己填的 `kNegBig` 承担。**两者完全不同。**

### 代价

最后一个列块现在按满宽 `kTileN` 处理（而不是 `nValid` 列）。对 `N` 恰好在块边界
附近的用例略增工作量，但比 `kTileN` 减半带来的拷贝调用增长小得多。
`kTileN` 本轮**保持 128**（它是上一轮的探针，本轮不动它，保证一轮只改一处）。

## 🎯 第 36 轮：判别实验 `kTileN` 256→128（已完成，结论见上）

### 观察到的事实

第 34 轮（orgM）12/15，失败 `{3: 50.00%, 5: 12.50%, 7: 6.25%}`；
第 35 轮（Kahan）13/15，失败 `{5: 12.50%, 7: 6.25%}`。

- 三个点**各自恰好只错 1 个输出元素**（B = 2 / 8 / 16）
- **Kahan 把测试点 3 清零了** ⇒ 3 的误差确实在 M 方向求和里 ⇒ 精度线是真的
- **但 5、7 连小数点都没动** ⇒ 它们的误差**不在我们的求和里**

### 推断

`y = Σ_m max_n C`，输入是 [-1,1] 均匀分布、`max_n` 有正偏 ⇒ `y` 通常是不小的正数；
**只有极少数 batch 的行最大值正负相消到接近 0**，此时 `rtol·|y| ≈ 0`，
判据只剩 `atol=1e-4`，C 的 fp32 累加误差（golden 是 fp64）就足以越界。

**关键**：这个误差**同时影响所有 batch**（它在 C 里，不是某个 batch 特有），
**只是只有 `|y|` 小的那个会越界** ⇒ 它是**小的系统性误差**，不是纯随机噪声。

### 实验设计

`kTileN` 256→128。**覆盖范围完全不变**（`colChunks` 4→2，列边界 0/256/512… → 0/128/256…），
只改**分解方式**。UB 从 64KB 降到 32KB。

| 结果 | 结论 |
|---|---|
| 失败元素换位置 / 数量变化 | 误差跟着**列边界**走 ⇒ 结构性 bug，继续挖列方向 |
| 5、7 仍是各自 1 个元素 | 误差跟着**数值**走 ⇒ fp32 C 的精度地板，改从 tiling 侧调 K 的累加粒度 |

**代价**：拷贝调用数 `tmCnt × ceil(N/kTileN)` 增约 35%，大用例会慢一些，但不至于 TLE。

## ✅ 第 35 轮：M 方向求和改补偿求和（Kahan）—— **13 / 15**

### 动机：第 34 轮之后，失败的性质**变了**

第 34 轮拿到 **12 / 15**，剩 3 个失败点：

| 测试点 | 错误占比 | 折算 |
|---|---|---|
| 3 | 50.00% | **1 / 2** |
| 5 | 12.50% | **1 / 8** |
| 7 | 6.25% | **1 / 16** |

**三个都恰好只错 1 个输出元素**（B 分别为 2 / 8 / 16）。这是数量级的性质变化：
之前是 100%（全错、结构性），现在是最小粒度。

而且"错的那一个"**在两次提交之间会移动**（第 31 轮已记过测试点 3 出现 50.00%；
测试点 5 在 100%/87.5%/75%/25%/12.5% 之间反复跳）。**同一份代码、位置来回翻**
⇒ 数值卡在容差边界上，不是逻辑错。

### 判据的边界在哪

`np.isclose(y, golden, rtol=1e-4, atol=1e-4)`。当某个 `y[b]` 因正负相消**接近 0** 时，
`rtol·|y| ≈ 0`，只剩 `atol=1e-4` 兜底 —— **此时唯一的误差来源就是求和精度**。

我们的 M 方向求和是**顺序标量 fp32 累加**，误差随项数**线性**增长；
而 golden 是 **FP64** 算的（仓库 `python/golden_pure.py`）⇒ 这是相消场景下最坏的算法。

### 改法

```cpp
float partial = 0.0f, partialC = 0.0f;
for (int32_t i = 0; i < tmCnt; ++i) {
    const float v = runningMax.GetValue(i * kReduceStride);
    const float yv = v - partialC;
    const float t  = partial + yv;
    partialC = (t - partial) - yv;
    partial  = t;
}
// partial 也以补偿方式累进 total
```

误差从 O(M·eps) 压到 O(eps)，代价是每项几个标量操作（M ≤ 几百，可忽略）。

⚠️ **依赖编译器不做浮点重结合**（`(t-partial)-yv` 不能被优化成 0）。
Clang 默认不开 fast-math，所以应该成立。**若本轮无效，下一个候选是"多个独立
累加器轮流累加再合并"**（那个不受重结合影响）。

### 顺带记一个**没有动**的东西

归约里 `repeatTime` 传的是 `baseM`(=64) 而**不是** `tmCnt`，所以最后一个 m 块会连
`[tmCnt, 64)` 那些**残留行**一起算（它们的 `cLocal` 是上一轮的脏数据）。
**这不影响正确性** —— 最终只读 `i < tmCnt` 的 `runningMax[2i]`。
只是白做功，属性能优化，**本轮不动**（一轮只改一处）。

## ✅ 第 34 轮：`SetOrgShape` 的 orgM 传错了 —— **12 / 15**

**结果：9 → 12。** `{1,2,4,6,8,9,10,11,12,13,14,15}` 通过，失败 `{3,5,7}`。

> 且失败模式从"结构性全错"变成"最小粒度"。

### 事实依据

官方样例 `dev/reference/matmul_reference.asc:143` 传的是**完整 M**：

```cpp
mm.SetOrgShape(tiling.M, tiling.N, tiling.Ka, tiling.Kb);
```

而我们从第 11 轮起一直传的是**每核 tile 高度** `kBaseM`：

```cpp
mm.SetOrgShape(kBaseM, N, K, K);   // ✗
```

### 为什么 orgM 就是 A 的行距

`SetOrgShape(orgM, orgN, orgKa, orgKb)` 描述的是**原始输入矩阵**的 shape。

| transposeX1 | x1 存储 | 沿 k 跨一步的步长 | 由哪个字段决定 |
|---|---|---|---|
| false | (M, K) | 1（连续） | 不需要 |
| **true** | **(K, M)** | **M** | **`orgM`** ← 只有它能承载 |

transposeX1=true 时，A 的 k 方向步长就是 M，而 orgN 是 C 的行距、orgKa/orgKb 是 K 的
范围，**唯一能承载 M 的字段只有 orgM**。传 64 ⇒ matmul 整片读错 A 的行距 ⇒ 100% 全错。

（注意本文件里 `taOff = b*(K*M) + tm0` **用的是真 M**，与传给 matmul 的 orgM=64
自相矛盾——这个不一致本身就是 bug 的指纹。）

### 与失败名单的吻合

## 🎯 第 33 轮：mb 循环的 scratch 双缓冲

失败的 6 个里，11、12 最大（3.5ms），而**同规模的 9、10 是通过的** ——

每核的 C scratch 只有一块，`mb` 循环之间**复用同一地址**：

- 上一 m 块的 `DataCopyPad`（MTE2 读 cGm）
- 与下一 m 块的 `mm.IterateAll`（FIX 写 cGm）

构成 **WAR 冒险**。UB 那层的同步管不到这里——它管 MTE2<->V，而这是 FIX(写 GM)
与 MTE2(读 GM) 之间，**只能靠地址隔离解决**。

若这个冒险稳定地输（cube 快、MTE2 慢），表现就是**确定性的 100% 错误**，
而非随机 —— 正好符合 11、12。

```cpp

// mb 循环内：

                        + (bmmsCoreIdx * 2 + bmmsParity) * bmmsScratchStride, baseM * N);
...
bmmsParity ^= 1;   // 下一次迭代换窗口
```

host 侧 scratch 乘 2。**这只影响 `numMBlocks > 1` 的用例**（M > 64），
对已通过的小用例（1/3/5/6/13/14）是行为不变的。

## 🎯 第 30 轮：opt7 —— N 分块下推到 matmul

### 动机（来自用时倍率的观察）

| 测试点 | 我们的用时 / 平台最优 | 结果 |
|---|---|---|
| 9、10 | 34~46x | 通过 |
| **11、12** | **82~87x** | 全错 |

**11、12 的处理代价是同规模通过用例的两倍**，说明它们有一个我们处理得特别差的

`n0` 偏移的跨行访问，代价按 `tmCnt × N/256` 增长。

### 改法

把 N 分块**下推到 matmul**，`singleCoreN` 固定为 `kTileN`：

```cpp
// host
tilingApi.SetOrgShape(kBaseM, N, K);      // orgN 仍是真实 N（决定 B 的行距）
tilingApi.SetShape(kBaseM, kTileN, K);    // ★ singleCoreN 固定 kTileN
cScratchElems = kBaseM * kTileN + kSlackElems;   // ★ scratch 不再随 N 增长
```

```cpp
// kernel：matmul 的四次调用整体搬进 n0 循环，每块只算 baseM x kTileN
for (n0 = 0; n0 < N; n0 += kTileN) {
    tbOffN = tbOff + (isTransB ? n0*K : n0);
    bGm.SetGlobalBuffer(x2 + tbOffN, ...);
    mm.SetOrgShape(kBaseM, N, K, K);
    mm.SetTensorA(aGm, isTransA);  mm.SetTensorB(bGm, isTransB);
    mm.SetTail(tmCnt, nValid);
    mm.IterateAll(cGm);
    ... DataCopyPad(cLocal[i*kTileN], cGm[i*kTileN], ...)   // ★行距恒为 kTileN
}
```

### 收益

1. **行距恒为 `kTileN`** —— 对齐常量，彻底消掉"行距 = N 非对齐"那一整类问题
   （第 11~19 轮反复纠缠的就是这一类）
2. **搬运变成整块连续**，不再有 `n0` 偏移的跨行访问
3. **scratch 固定 64KB**，不再随 N 增长

保留：TQue 同步、`[nCopy, kTileN)` 的 `kNegBig` 填充。

### 回退配方（若不通过数下降或出现卡死）

1. host：`SetShape(kBaseM, N, K)`；`cScratchElems` 用 `kBaseM*N + kSlackElems`
2. kernel：把 `SetOrgShape/SetTensorA/SetTensorB/SetTail/IterateAll` 移回 n0 循环**之前**
   （`bGm` 用 `tbOff`，`SetTail(tmCnt, N)`），拷贝源改回 `cGm[i*N + n0]`
3. 即回到「opt5 + 填充」那一版（实测 8/15）

## 🔑 第 27 轮：找到"全 Wrong + 用时整列 `-`"的真正原因

仓库 `op_kernel/kernel_opt6.asc` 的注释原文：

```cpp
AscendC::WaitFlag<AscendC::HardEvent::MTE2_V>(evtM2V);
AscendC::SetFlag<AscendC::HardEvent::V_MTE2>(evtV2M);
AscendC::WaitFlag<AscendC::HardEvent::V_MTE2>(evtV2M);
...
// 函数末尾必须成对释放
```

### 两处修复

**★OPT-1 每核一份独立的 C scratch**

```cpp
const int64_t bmmsCoreIdx = GetBlockIdx();
const int64_t bmmsScratchStride = static_cast<int64_t>(baseM) * N + kSlackElems;
cGm.SetGlobalBuffer(reinterpret_cast<__gm__ float*>(cScratchGm)
                        + bmmsCoreIdx * bmmsScratchStride,
                    static_cast<uint32_t>(baseM * N));
```

原来所有核都往 `cScratchGm` 的**同一个裸地址**写自己的 C 分片 —— 多核并发时
**互相覆盖**。这正是"结果不可复现 / 只覆盖前几列 / 大 shape 必错"的根因：
**形状越大，别的核写进来的时间窗越长。** host 侧 scratch 大小要相应乘 `blockNum`，
且 `blockNum` 必须在 malloc 之前算出来。

**★SYNC-1 / SYNC-2 UB 流水同步必须手动插**

```cpp
// DataCopyPad 循环之后：MTE2(写 cLocal) -> V(读 cLocal)，防 RAW
AscendC::SetFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
AscendC::WaitFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
// colChunks 归约循环之后：V(读完) -> 下一轮 MTE2(覆盖)，防 WAR
AscendC::SetFlag<AscendC::HardEvent::V_MTE2>(EVENT_ID1);
AscendC::WaitFlag<AscendC::HardEvent::V_MTE2>(EVENT_ID1);
```

依据官方《关键特性说明》：
- cce-auto-sync **表 3** 中 `MTE2→V` 与 `V→MTE2` 均标为 `-`，**不自动插入**
- TPipe-TQue 的自动同步**要求"正确使用 AllocTensor/EnQue/DeQue/FreeTensor"**；
  本文件用裸 `TBuf` + 直接 `DataCopyPad`/`WholeReduceMax`，**不满足该约束**
- 官方**反例 2** 与本处结构逐行同构，原文明确说会导致"样例执行失败"

避坑：`SetFlag`/`WaitFlag` 必须成对且参数一致，否则 timeout 卡死；
**不要用 `EVENT_ID6`/`EVENT_ID7`**（6 系统预留，7 被 TPipe 占用）。

## 🎯 第 20 轮：找到了 —— `IterateAll` 是**异步**的，我们从没等过

**触发怀疑的事实**：第 16 轮（3 Pass）和第 18/19 轮（全挂）的代码几乎一致，
却给出完全不同的结果。**同一份代码、不同结果 ⇒ 竞态。** 而题目规则 1
明确要求"多次执行结果完全一致"。

回头去查那条一直挂在 [VERIFY] 里、却从没验证过的东西 —— `IterateAll` 的签名：

```cpp
IterateAll(const GlobalTensor &gm, uint8_t enAtomic = 0, bool enSequentialWrite = false,
           bool waitIterateAll = false, bool fakeMsg = false)
```

**`waitIterateAll` 默认 `false`**，文档原文：

> false：不需要通过 WaitIterateAll 接口等待 IterateAll 执行结束，
> **开发者自行处理等待 IterateAll 执行结束的过程**。

**我们的代码 `mm.IterateAll(cGm);` 之后立刻就 `DataCopyPad` 去读 `cGm`** ——
等于在读一个**只写了一部分**的 C 矩阵，读到哪一列取决于 cube 当时算到哪。

### 这一个竞态解释了本轮之前**所有**解释不通的现象

| 现象 | 竞态解释 |
|---|---|
| `k_eff ≈ 9`（case1 的行 max 在第 14 列→错，case2 全在第 8 列内→对） | 读的时候只写好了前几列 |
| 同 shape 一错一对（测试点 2 vs 3） | 同上，取决于该 case 的行 max 落在哪一列 |
| 同一份代码两次跑出不同结果（16 轮 vs 18/19 轮） | 竞态本就不可复现 |
| 第 17 轮"固定长度拷贝"让测试点 13 掉下来 | 改变了时序，竞态结果随之改变 |
| "全挂 + 用时全 `-`" | 读到的 C 几乎是空的，kernel 早早走完 |

> 反过来看：前面若干轮我一直在改**搬运和归约**（长度、填充、mask、对齐），
> 那些都不是根因，所以怎么改都只在"竞态结果的分布"里打转。

### 修法（官方写法，`WaitIterateAll.md`「调用示例」逐字）


## 🎯 第 15 轮：真正的修法（一次满足三个约束）

`Duplicate` 的约束说明明确指向通用对齐规则，而表 2 要求 **UB 起始地址 32B 对齐**。
所以第 11/14 轮那个从 `nValid` 起刷的写法，在 `nValid % 8 != 0` 时**是违规的** ——
这是当前基准版里确凿的一条 bug。

这里有三个约束要同时满足：

| # | 约束 | 来源 |
|---|---|---|
| 1 | UB 起始地址 32B 对齐 | 通用说明和约束 表 2 |
| 2 | 本行最后一个不满 32B 的块里，`[nValid, 块尾)` 装的是**下一行的数据**，不能参与 max | 行距 = N |
| 3 | 补齐的列必须是 `kNegBig`，不能是 0 | 题面 3.7 |

- 旧写法（`DataCopy` + 从 `nValid` 起 `Duplicate`）：满足 2、3，**违反 1**
- 第 13 轮改成从 `alignUp8(nValid)` 起刷：满足 1、3，**放跑了 2**
- **正解**：用 `DataCopyPad` 自带的右侧填充

```cpp
const int32_t nCopy = (nValid + 7) & ~7;   // alignUp8
const int32_t nPad  = nCopy - nValid;      // 0..7 个元素 ≤ 28 字节

DataCopyExtParams cp{1, (uint32_t)(nValid * sizeof(float)), 0, 0, 0};
DataCopyPadExtParams<float> pad{true, 0, (uint8_t)nPad, kNegBig};   // isPad=true
DataCopyPad(cLocal[i*kTileN], cGm[i*N + n0], cp, pad);   // 精确搬 + 右侧补 kNegBig
// [0, nCopy) 全是合法内容；[nCopy, kTileN) 起点天然是 8 的倍数 ⇒ Duplicate 合法
if (nCopy < kTileN) { Duplicate(cLocal[i*kTileN + nCopy], kNegBig, kTileN - nCopy); }
```

三个约束一次满足。附带好处：
- `blockLen + nPad*4 = nCopy*4` 恰好 32B 对齐 ⇒ 框架**不会再追加随机 dummy**
- `nPad ≤ 7 元素 = 28 字节`，在文档"不能超过 32 字节"的限制内
- 不再越读，`kSlackElems` 退化为纯防御
- 判据用 `nCopy` ⇒ 天然避开零长度 `Duplicate`

## 🐛 第 13 轮：真正的对齐 bug（UB 侧）

顺着上面那条规则回看代码，发现真正违规的地方是尾块掩码：

```cpp
Duplicate(cLocal[i * kTileN + nValid], kNegBig, kTileN - nValid);
//                             ^^^^^^ nValid=1/19/65/257 时 → 4/76/260/1028 字节
//                                    都不是 32 的倍数 ⇒ UB 起始地址未对齐 ⇒ 非法
```

`nValid % 8 != 0` 时这个起点就不是 32B 对齐的。本地用例里 **N=1/19/65/257
全都会命中**（N=8/16/32/40/64 则没事）。

**修法**：从 `alignUp8(nValid)` 开始刷，而不是从 `nValid`。

```cpp
const int32_t nCopy = (nValid + 7) & ~7;          // 拷贝长度，32B 对齐
DataCopy(..., blockLen = nCopy / 8, ...);         // 只写到 [0, nCopy)
if (nValid < kTileN) {
    Duplicate(cLocal[i * kTileN + nCopy], kNegBig, kTileN - nCopy);
    //                          ^^^^^ 恒为 8 的倍数 ⇒ 32B 对齐 ✓，且不重不漏
}
```

拷贝长度上取整多读的那几个元素，落在 scratch 的 `kSlackElems` 余量里，
随后被这次 `Duplicate` 覆盖 —— 既有设计正好接得住。

|---|---|---|---|---|---|---|---|
| case0 | 1 | 1 | 1 | 32 | fp16 | 0 | 0 |
| case1 | 1 | 16 | 16 | 32 | fp16 | 0 | 0 |
| case2 | 1 | 16 | 16 | 32 | fp16 | 0 | 0 |

**三个结论（直接影响设计）**：

1. **shape 极小**：M ≤ 255、N ≤ 257、K ≤ 64。M=1、N=1 这种退化用例真实存在。
2. **普遍不对齐**：N = 1 / 19 / 65 / 257 都不是 8 的倍数。
   ⇒ `WholeReduceMax` 的 `srcRepStride` 以 datablock(32B) 为单位，
   **行距不是 8 的倍数的行根本没法直接用 repeat 归约**。
   任何「一行 = 一个 repeat」的写法在这些用例上都是错的。
3. **`SetShape(kBaseM=64, N, K)` 在 N=1 时是退化的**：singleCoreN=1，
   而 baseN 必须是 16 的倍数 —— tiling 只能压到 1/8/16。
   M=1 时 singleCoreM=64 也是虚报的。**这正是 Matmul 高阶 API 覆盖最差的角落**，
   而整个方案压在它上面。开发时一次都没看过这份数据，是重大疏忽。

第 11 轮的归约设计就是针对第 2 条做的：**逐行把 C 搬进 UB，UB 内行距固定为
kTileN=256（64 的倍数）**，于是每行都 32B 对齐、每个 repeat 恰好是行内一段，
布局假设才真正成立。

## ✅ 第 9 轮：两个根因已从官方文档/样例坐实（不需要再猜）

依据：`hicann/asc-devkit` commit `c8c1b9d`（对应 CANN 9.0.0）的
`docs/api/context/WholeReduceMax.md`、`docs/api/context/GetTensorC.md`、
`docs/api/context/IterateAll.md`，以及官方样例 `matmul_leakyrelu.asc`。

### 根因 1：`WholeReduceMax` 的 dst 布局是 stride **2**，不是 8

`WholeReduceMax.md` 参数表原文：

- `order` 默认值 `ORDER_VALUE_INDEX`，此时「返回结果存储顺序为 **[value, index]**」
- `dstRepStride`：「**返回索引和最值时，单位为 dst 数据类型所占字节长度的两倍**」
  （fp32 → 8 Bytes）

官方「完整样例」直接印证：src 1024 个 half、`mask=128` → `repeat=8`，
而 **`dstDataSize = 16`** —— 8 个 repeat 产出 16 个元素，正是每 repeat 2 个。
样例结果 `[9.980e-01, 5.364e-06]` 即 `[value, index]`。

⇒ 第 i 行的 max 在 `dst[2*i]`。旧代码读 `runningMax[i*8]`，
除 `i=0` 外全读错行或读到索引位 → **这就是 15/15 全 100% 的直接原因**。

> ⚠️ **推翻本文档旧版的「一步诊断」**：旧版建议把 `kReduceStride` 由 8 改成 1 试一次。
> 那个实验会给出**误导性结论** —— 8→1 同样是错的，错误率照样会变，
> 你会据此判定「是布局假设问题、方向锁定」，然后沿着错方向继续。
> **正确值是 2**（或改用 `ReduceOrder::ORDER_ONLY_VALUE`，此时单位为 dtype 字节长度、stride = 1）。

### 根因 2：C 落 UB 这条路**根本没有 ND 行主序这种形态**

比旧版估计的更严重，两点铁证：

1. `GetTensorC.md` 明确：`c/co2Local` 输出 ——「取出 C 矩阵到 VECIN，
   **数据格式仅支持 NZ**」。NZ 是分形布局，不是行主序 `baseM×baseN`。
2. 官方 matmul+vector 融合样例 `matmul_leakyrelu.asc` 用的是
   `TPosition::VECIN`（**不是 `VECCALC`**），且配合 `TQue<VECOUT>`、
   `Iterate<true>()`、`GetTensorC<true>(dst, false, true)`、循环后 `mm.End()`。

⇒ 旧代码里这两处前提同时失效：
- `cLocal[i * baseN + nValid]`（按行主序定位 N 尾块）
- `WholeReduceMax(..., srcRepStride = baseN/8)`（假设「一行 = 一个连续 repeat」）

**这不是改个常量能修的**，所以第 6/7/8 轮怎么改都还是 100%。
`Toposition::VECCALC` 本身也不对（应为 `VECIN`），但改成 `VECIN` 拿到的是 NZ，一样归约不了。

### 第 9 轮的修法：C 改走 GM

只有输出到 **GM** 时才支持 **ND**。改动：

1. `CType` → `MatmulType<TPosition::GM, CubeFormat::ND, float>`；host 侧 `SetCType` 同步改
2. `run_kernel` 里 `aclrtMalloc` 一块 `baseM*baseN*sizeof(float)` 的 scratch，作参数传入
3. `mm.template GetTensorC<true>(cGm, 0, /*esw*/true)` —— `enSequentialWrite=true`
   让每片都**连续写到 scratch 开头**，于是 scratch 只需 `baseM*baseN`（约 64KB），
   **与 N 无关**，不受「B*M*N 无约束」影响
4. 整体 `DataCopy` 进 UB → 此刻 UB 里才真正是行主序 `baseM×baseN`
5. 再掩 N 尾块 → `WholeReduceMax` 行归约（`kReduceStride = 2`）
6. 循环后补 `mm.End()`

顺带修掉两个隐患：`baseM` 统一取 `tiling.baseM`（旧版硬编码 64 与 tiling 来源不一致）；
`aGm` 长度按该 batch 剩余真实元素数给（旧版虚报 `baseM*K`，M 尾块会越界读）。

### 第 9 轮首次提交的编译错误（已修，记下来免得再踩）

报错：

```
kernel.asc:354:65: error: no member named 'baseM' in 'optiling::TCubeTiling';
                         did you mean 'baseM_'?
kernel.asc:355:67: error: no member named 'baseN' in 'optiling::TCubeTiling';
                         did you mean 'baseN_'?
```

**根因**：host 侧的 `optiling::TCubeTiling` 是用 `TILING_DATA_FIELD_DEF(int32_t, baseM)`
宏（`register/tilingdata_base.h`）生成的，真实成员是 `baseM_`，外部访问不到。
注意这只影响 **host 侧**那个结构体；kernel 侧 `kernel_tiling/kernel_tiling.h`
里的 `TCubeTiling` 是普通结构体，`tiling.baseM` / `tiling.baseN` 正常可用
（第 8 轮的 `tiling.baseN` 就编译通过）。两个同名结构体别搞混。

**修法**：不读那个字段，改用 `MultiCoreMatmulTiling::SetFixSplit(baseM, baseN)`
把 baseM/baseN **钉死**，之后用常量算 scratch，两边必然一致。

查证到的关键事实（来自 `impl/adv_api/tiling/matmul/matmul_tiling_base.cpp`）：

- `SetFixSplit(int32_t baseMIn = -1, int32_t baseNIn = -1, int32_t baseKIn = -1)`
  —— **三个参数都有默认值**，传 `-1` 表示该项自动
- 它要求 `baseMIn % C0_SIZE == 0`，否则返回 `-1`；64 / 256 均满足
- `adjust_`（即 baseM/baseN 的上下界）**只在构造函数、`SetFixSplit`、`SetSplitRange`
  里被赋值**，`SetShape` / `SetOrgShape` 不碰它 ⇒ 先 `SetShape` 再 `SetFixSplit` 安全
- ⚠️ `GetBaseM()` / `GetBaseN()` 返回的是**成员变量**，而该成员**只在 `SetFixSplit`
  里被赋值**（构造函数置 -1）。**没调 `SetFixSplit` 时它返回 -1**，
  并不是「tiling 自动选出的值」——别指望用它读回自动 tiling 的结果。

钉死后的附带好处：`baseN = 256` 必为 64 的倍数 ⇒ 行归约快路径恒成立；
`cBuf = 64*256*4 = 64KB`，UB 预算不再取决于 tiling 的心情。

### 第 9b 轮的 Profiling 报错（已修）：别用 SetFixSplit 钉死 baseN

报错：

```
Profiling rule violated: each iteration must launch exactly 1 kernel.
Expected 75 launches, got 30.
```

**读法**：`75 = 15 用例 × 5 轮`，`30 = 6 用例 × 5` ⇒ **有 9 个用例一次 kernel 都没启动**。

**根因**：`SetFixSplit(64, 256)` 把 baseN 强制成 256。N < 256 的用例
（小 shape、N=1 之类的冒烟用例）tiling 不可行 → `GetTiling()` 返回 -1 →
`run_kernel` 第 343 行提前 `return` → **一次 launch 都没有** →
平台按「每次 run_kernel 必须恰好启动 1 个 kernel」判定违规。

排查依据：第 8 轮是 WA 而非 profiling 违规 ⇒ 当时 75 次 launch 全都在，
`GetTiling` + 3 个 `aclrtMalloc` 对全部 15 个用例都是成功的。
第 9b 相对第 8 轮的**唯一新增失败路径就是 SetFixSplit 这一条**。

> 教训：`run_kernel` 里每一处提前 `return` 都会表现为「launch 数不足」，
> 而不是「结果不对」。加早退前先想清楚它在小 shape 上会不会命中。

**修法**：改用 `SetSplitRange(-1, kMaxBaseN)`（只设**上界**，min 传 -1 = 不动）。
实现里它只写 `adjust_.maxBaseN`，算法仍可在 `[minBaseN, 256]` 内自由取值，
小 N 用例照常工作。同时拿到想要的上界：
`baseM(≤ singleCoreM=64) × baseN(≤256) ≤ 16384 元素 = 64KB`，
于是 scratch 和 UB 都按这个上界开，host 侧依然不必去读
`optiling::TCubeTiling` 的私有 `baseM_`/`baseN_`。
