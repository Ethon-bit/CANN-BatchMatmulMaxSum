## 一、这道题到底在做什么？

一句话：**把三段计算合并成一段，并且让它跑在 NPU 上。**

### 先用大白话说清楚业务

想象你在做一个"搜索问答"系统。用户问了一句话（query），你有一堆文档（document）。
你要判断：**哪篇文档和这个问题最相关？**

ColBERT 这个模型的做法是：

1. 把 query 切成若干个小片段（token），每片变成一个向量。假设有 M 片，每片 K 个数 → 得到一个 $M \times K$ 的矩阵。
2. 把 document 也切成 N 片，每片 K 个数 → 得到一个 $K \times N$ 的矩阵（转置一下方便相乘）。
3. **让每一片 query 和每一片 document 两两算相似度**（就是向量点积）。这叫"批量矩阵乘"，得到 $M \times N$ 的相似度表格。
4. **对每个 query 片段，挑出它和所有 document 片段里最像的那个**（取最大值）。这叫 MaxSim，得到 M 个数。
5. **把这 M 个数加起来**，得到 1 个总分。分数越高越相关。

### 翻成数学

| 步骤 | 数学 | 代码里的对应 |
| :--- | :--- | :--- |
| 批量矩阵乘 | $A[b,m,n] = \sum_k X_1[b,m,k] X_2[b,k,n]$ | `torch.bmm` |
| MaxSim | $R[b,m] = \max_n A[b,m,n]$ | `torch.amax(..., dim=-1)` |
| 求和 | $y[b] = \sum_m R[b,m]$ | `torch.sum(..., dim=-1)` |

$b$ 是"第几组数据"。比如你一次处理 8 个 query-document 对，那 B=8，每组各算各的，互不干扰。

### 为什么叫"融合算子"？

在 PyTorch 里，上面三步是**三个独立的操作**，每个都要：

1. 把数据从显存读进来
2. 算
3. 把结果写回显存

中间那个 $M \times N$ 的相似度矩阵可能非常大（M 和 N 最大都能到 8192，那就是 6700 万个数字）。**写了又读、读了又写，全是浪费。**

"融合"的意思是：**让数据进了 NPU 的计算单元之后，一口气把三步算完再出来**，中间结果尽量留在片上的快速缓存里，不来回搬运。

赛题原话："融合后可减少 Kernel Launch 与中间数据搬运。"

## 二、为什么这题对 Python 选手门槛高？

因为你要从"调库的人"变成"造库的人"。区别在于：

| | Python / PyTorch | Ascend C 算子开发 |
| :--- | :--- | :--- |
| 你写什么 | `torch.bmm(a, b)` | 手写多层循环 + 手动管理搬运 |
| 谁管内存 | 解释器 | **你自己** |
| 数据在哪 | 一个变量名 | 分 5 个层级，你得手动搬 |
| 谁管并行 | 框架 | **你自己**（切分给多个核） |
| 怎么调试 | `print()` | 编译上板 + msprof 性能分析 |

**最关键的心智转变**：在 NPU 上，数据不是"在哪都能取"，而是分成好几层，越靠近计算单元越快越小：

```
GM（全局内存，最大最慢）
  ↓ 搬运
L1 / L0（片上缓存，快）
  ↓
Cube 单元（算矩阵乘）/ Vector 单元（算逐元素和归约）
  ↑
UB（统一缓冲区，Vector 的工作台）
```

**搬运数据的时间往往比计算还长。** 所以这道题的核心竞争力不是"算得快"，而是"**搬得少、搬得巧**"。

## 三、赛题埋的几个坑（务必注意）

这三个坑是赛题**专门设计来筛人**的，都能在示例里找到对应：

### 坑 1：MaxSim 的初值不能是 0

新手最自然的写法是 `max_val = 0`，然后遍历取最大。
但如果这一行相似度**全是负数**，你的结果是 0，正确答案是那个最大的负数。

👉 对应赛题**示例3**，正确答案是 `-1.0`，不是 `0`。

正确做法：初值设成 `-inf`（负无穷），或者直接用这一行的第一个元素当初值。

### 坑 2：Max 和 Sum 不能交换

数学上看着好像能换，实际上**不能**：

$$\sum_m \max_n A[m,n] \ne \max_n \sum_m A[m,n]$$

举个反例就明白了：矩阵 `[[1, 5], [3, 2]]`

- 先 max 再 sum：max(1,5)=5，max(3,2)=3，加起来 = **8**
- 先 sum 再 max：1+3=4，5+2=7，取最大 = **7**

8 ≠ 7。所以赛题把它列为"归约顺序规则"，写错了直接零分。

### 坑 3：transpose 只是"数据的摆放方式"

赛题反复强调：`transposeX1` / `transposeX2` **只声明存储形状，不代表要真的做转置**。

这是什么意思？同一份逻辑数据，在内存里可以有两种摆法：

```
逻辑上 x1 是 [B, M, K]（M 行 K 列）

摆法A（transposeX1=false）：一行一行存，内存里是 M 行 K 列
摆法B（transposeX1=true）：一列一列存，内存里是 K 行 M 列
```

**数据还是那些数据，算出来的结果必须一模一样。** 但你的读取代码必须知道"现在内存里是按哪种方式摆的"，才不会读错。

赛题要求**四种组合全部支持**：

| transposeX1 | transposeX2 | x1 存储 | x2 存储 |
| :---: | :---: | :--- | :--- |
| false | false | $[B,M,K]$ | $[B,K,N]$ |
| false | true | $[B,M,K]$ | $[B,N,K]$ |
| true | false | $[B,K,M]$ | $[B,K,N]$ |
| true | true | $[B,K,M]$ | $[B,N,K]$ |

👉 这就是为什么 `python/golden_pure.py` 里要写那两个 `get_x1` / `get_x2` 小助手函数——就是为了优雅地处理这四种情况。

## 四、评分怎么算？

$$\text{score} = \frac{100}{1 + \log_{1.5}\left(\dfrac{t}{T}\right)}$$

- $T$ = 目前全场最优耗时
- $t$ = 你的耗时

**先看几个点感受一下这个公式：**

| 你的耗时 | $t/T$ | 得分 |
| :--- | :--- | :--- |
| 和最优一样快 | 1.0 | **100** |
| 慢 1.5 倍 | 1.5 | **50** |
| 慢 2.25 倍（1.5²） | 2.25 | **33.3** |
| 慢 3.4 倍 | 3.4 | **25** |
| 比最优快（不可能，但数学上） | 0.67 | **∞** |

**关键结论：**

- 这个函数**对慢的惩罚是递减的**，但对快的奖励很陡。从"慢 3.4 倍"提升到"慢 1.5 倍"，分数从 25 涨到 50 —— **翻倍**。
- **15 个测试点必须全部精度通过才计分。** 有一个挂了，这题就是 0 分。所以**正确性优先于性能**，先把功能写对，再谈优化。
- 最终分数是 15 个 case 的**均值**。

## 五、建议的动手顺序

不要一上来就写 Ascend C。按这个顺序走，每一步都有明确的"做完了"标准：

### 第 1 步：先让 Python 版跑通 ✅（已完成）

```bash
python python/golden_pure.py
```

**做完的标志**：3 个示例全部打印"通过"。这是你的"标准答案"，后面所有工作都拿它做对比。

### 第 2 步：吃透四种存储布局

打开 `python/golden_pure.py`，重点看 `get_x1` / `get_x2` 两个函数，想明白为什么 `transpose_x1=True` 时下标要写成 `x1[b][k][m]`。

**做完的标志**：你能自己解释示例2 为什么输出还是 2.0。

### 第 3 步：跑通交叉验证

```bash
uv run --with torch python test/cross_check_golden.py
```

**做完的标志**：6 种形状 × 4 种布局 = 24 个组合全部 OK。这证明你的 Python 理解是对的。

### 第 4 步：搭起算子工程（就是本仓库的骨架）

看 `op_host/` 下的算子原型定义，理解"输入是什么、输出是什么、属性是什么"是怎么声明给框架的。这部分**基本是填空题**，照着本仓库的骨架改就行。

**做完的标志**：能编译通过。

### 第 5 步：**先写一个"能跑但对"的朴素版 kernel**

⚠️ **这一步千万不要追求性能。**

用最笨的写法：一个核处理一个 batch，老老实实按三层循环算。
目标只有一个：**精度测试全过**。

**做完的标志**：15 个测试点精度全绿。

### 第 6 步：再谈性能优化

有了正确的基线之后，按这个优先级优化：

1. **多核切分** —— 沿 B 维切（B 最大 64），B 小于核数时沿 M 维再切
2. **尾块处理** —— M/N 不是 16 的倍数时别越界
3. **Double Buffer** —— 让搬运和计算重叠起来，这是提速最大的一招
4. **Cube/Vector 协同** —— 矩阵乘交给 Cube，归约交给 Vector

**做完的标志**：用 `msprof` 看到 Cube 和 Vector 利用率明显上去了。

## 六、这个仓库怎么用

```
op_host/     ← 算子原型 + Tiling（"告诉框架这个算子长什么样、怎么切"）
op_kernel/   ← 真正的 Ascend C 核函数（"算"）★ 你主要要写这里
op_api/      ← 单算子调用接口（"让外部能调它"）
python/      ← 参考实现（"标准答案"）
test/        ← 测试和精度比对（"检查你写得对不对"）
docs/        ← 你正在看的文档
```

**当前状态**：`python/` 是完整可用的；`op_host/` / `op_kernel/` / `op_api/` 是**带详细注释的骨架**，需要你按 TODO 填实现。详见根目录 `README.md` 的状态表。
