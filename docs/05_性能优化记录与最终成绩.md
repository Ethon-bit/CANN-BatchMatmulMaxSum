## 二、瓶颈到底在哪（msprof 硬结论）

```bash
msprof --application="./dev/build/bmms_dev dev/data/input/caseN /tmp/yN.bin" \
       --output=/tmp/pN --aic-metrics=PipeUtilization
```

| case | shape | dur | **aic_scalar** | aic_mac | aic_fixpipe | aiv |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: |
| 0 | 1×1×1×32 | 14.72µs | **11.57** | 0.037 | 1.94 | 9.41 |
| 13 | 1×255×257×40 | 67.14µs | **63.04** | 0.532 | 25.94 | 35.57 |
| 9 | 1×1×8191×32 | 179.4µs | **139.26** | 1.689 | 48.80 | 91.53 |
| 10 | 1×8191×1×32 | 994.2µs | **957.14** | 2.809 | 90.21 | 499.15 |

### 结论一：瓶颈在 matmul 高阶 API 内部，不在我们的代码里

**`aic_scalar`（Cube 核的标量单元）占用 68~95%，而真正的矩阵乘 `aic_mac` 只有 0.9~23%。**

**决定性实验（消融探针）**：把 n0 拷贝-归约循环、逐行 Duplicate、Kahan 逐行求和
**全部删掉**，其余一字不动：

| case | 完整版 | 只留 matmul | 变化 |
| :--- | ---: | ---: | :--- |
| 10 | 994.200µs | 998.600µs | +0.4%（噪声内） |
| 13 | 67.140µs | 66.600µs | −0.8% |
| 0 | 14.720µs | 14.160µs | −3.8% |

> **⇒ 我们自己的向量代码对耗时贡献 ≈ 0。**
> **⇒ 改归约 / 搬运 / 掩码 / repeatTime / 列块分解 —— 全部无效，因为它们在关键路径之外。**

### 结论二：地板 ≈12.7µs，来自 `REGIST_MATMUL_OBJ` / 初始化

`1×1×1×32` 这种平凡用例也要 **12.7~14.7µs**。把 matmul 的五次调用
（`SetOrgShape`/`SetTensorA`/`SetTensorB`/`SetTail`/`IterateAll`/`End`）**全部跳过**，
也只降到 13.2µs ⇒ **钱花在注册和初始化上，不在调用上。**

而评测里**最优解只要 1.25µs** ⇒ 小测试点的差距**全部**是这块地板。

### 结论三：拟合出的成本模型

```
dur ≈ 12.7µs  +  0.26ns × (M·N)  +  119ns × M  +  20ns × N
```

四个测例全部命中（case0 14.7 / case13 67.9 / case9 179 / case10 990，实测 14.72 / 67.14 / 179.4 / 994.2）。

**主导项是 `119ns × M`** —— 每多一行 M 付 119ns（≈214 周期），而一行只算 32 次乘加。

## 三、最终方案：给极小 shape 加一条纯向量通路

新增内核 `bmms_vec<T>`：**里面完全没有 Matmul 对象**，所以没有那 12.7µs 的地板。

```
acc[0..N) = Σ_k x1[m,k] · x2[k, 0..N)      // Axpy
rowMax    = max_n acc                       // WholeReduceMax
total    += rowMax                          // Kahan（沿用第 35 轮的精度修法）
```

host 侧按 shape **二选一**启动（每次 `run_kernel` 仍然只启动 1 个 kernel）：

```cpp
const bool useVecPath = (!transposeX1) && (!transposeX2)
    && (M > 0) && (N > 0) && (K > 0)
    && (M * K <= 128) && (N <= 8) && (K * N <= 8192);
```

**守卫边界是实测出来的**（同一环境，case13 做环境锚点）：

| case | shape | VEC | main | 谁赢 |
| :--- | :--- | ---: | ---: | :--- |
| 0 | 1×1×1×32 | **7.94** | ~12.7 | VEC ✅ |
| 11 | 64×4×4×32 | **32.82** | ~48 | VEC ✅ |
| 1/2 | 16×16×32 | 17.70 | **13.24** | main |
| 3 | 17×19×40 | 23.24 | **13.66** | main |

**为什么守卫不能再放宽**：向量通路的成本 ≈ `5.8µs + 19ns × 调用数`，
而调用数 ≈ `2K + M×(K+3)`。对 `16×16×32` 是 624 次 ⇒ 17.6µs，**输给主通路的 12.16µs**。
其中 512 次是 `M×K` 的 Axpy，是这个算法的本质，动不了。

### 实测收益（平台）

| 测试点 | 加向量通路前 | **加之后** | 变化 |
| :--- | ---: | ---: | :--- |
| **1** | 14.15µs | **5.78µs** | **−59%** |
| 2~15 | — | — | 均在噪声内，**无任何倒退** |

测试点 1 的比值 11.3× → 4.62×，得分 14.3 → **20.9**。

## 四、❌ 已封死的方向（**别再试，重复 = 白烧一轮**）

| 改动 | 结果 |
| :--- | :--- |
| 改 matmul tiling 参数（`SetFixSplit` 等） | 7 次尝试全败，`aic_scalar` 纹丝不动 |
| `DataCopyPad` 合并整块行（`blockCount=rows`） | 正确性崩（`dstStride` 的 UB 布局与假设不符） |
| `__aicore__` → `__mix__` | 编译失败（CANN 9.0.0 不认该限定符） |
| **N 分块下推**（`singleCoreN = kTileN`） | 正确性崩，**且架构上不可行**：`orgN` 同时是 B 的行距和 C 的行距，**不能分别设置** |
| 归约改逐行（`repeatTime=1`） | **TLE**（代价 ×64） |
| `srcRepStride` 改 gap 语义（32→24） | 崩到 1/15 ⇒ **确认它语义就是「绝对跨距」** |
| 收窄 `DataCacheCleanAndInvalid` 范围 | 无收益（测试点 1 整个 kernel 才 5.78µs，说明它根本不贵） |
| **`kBaseM=128` + 运行期 `mbRows`** | **平台 1/15 / TLE，且同一份代码两次结果不同 ⇒ 概率性卡死，永久封存** |

## 五、⚠️ 踩过的坑与由此确立的判据

### 1. 本地全绿 ≠ 平台能过（**最贵的一课**）

本地两个验证工具**都是每个用例开一个独立进程**：

| 工具 | 调用方式 |
| :--- | :--- |
| `run_case.sh all` | 每个 case 一个独立进程 |
| `sweep.py` | `subprocess.run` —— 每个组合一个独立进程 |

**而平台是把 15 个 shape 放在同一个进程里依次调用（每个 5 次）。**
⇒ **跨 launch 的状态问题（cache 残留、事件 ID、GM 复用）在本地永远测不出来。**

### 2. 判据：偶发失败一律整体放弃

| 失败形态 | 处理方式 |
| :--- | :--- |
| **稳定失败**（每次都挂） | 可以定位、可以修 |
| **偶发失败**（时好时坏） | **必须整体放弃** —— 无法验证，且会**伪装成成功** |

我们提交 `kBaseM=128` + `mbRows` 那次：第一次 **TLE**，第二次**全 Wrong + 用时整列 `-`**，
**同一份代码两种结果**。若某次侥幸 15/15，就会把一个随时会炸的地雷当成好版本发出去。

**⇒ 不能复现平台调用形态的前提下，任何"偶发"的改动都不能进提交物。**

### 3. `msprof` 之前**必须重新编译**

`msprof` 不会编译，它只是拿 `dev/build/bmms_dev` 这个**已存在的二进制**去跑。
我们有三轮（第 56/57/60 轮）测的其实是**上一次的内核**，结论全部作废。

> **记法：改了 `kernel.asc` → 先 `bash dev/run_case.sh all`（会 `cmake && make`）→ 再 msprof。没有例外。**

### 4. 「用时」列是最灵敏的回归判据

- `用时` 为 `-` ≡ **该测试点的 kernel 几乎没干活**（常见的两种成因：超时/卡死，或太快没进阈值）
- 通过数会抖（±2 是采样噪声），但**用时一旦数量级变化就是确定性损坏**
  （例：测试点 9 从 2.43ms → 1.33µs）
- 看用时**不能只看通过数**

## 六、给后来人的建议

1. **先读这份文档和 [docs/04](04_根因报告-写GM未回写cache.md)**，再动手。
   这两份合起来记录了 70+ 轮的失败方向，能省掉大量重复劳动。
2. **不要在 matmul 高阶 API 外面做优化** —— 消融实验已经证明它们贡献 ≈0。
   要动只可能动 API 内部（改不了）或者换掉它（纯向量/手写 cube 指令）。
3. **如果要做纯向量通路**：它的成本是 `5.8µs + 19ns × (2K + M(K+3))`。
   只有 `M*K ≤ 128 且 N ≤ 8` 时才划算 —— 这个边界是实测出来的，别凭感觉放宽。
4. **提交前**：`run_case.sh all`（15/15）+ `sweep.py --quick`（240 组合）+ `grep printf`（无输出）。
5. **最终目标应该是小测试点**（占 72% 分数），它们只要从 5 倍差距压到 1 倍就是满分区间；
   而大 shape 无论怎么优化都是 6~10 分，**投入产出比差 100 倍以上**。
