## 二、已经确认的事实（有证据，不是推测）

### 2.1 数据类型 / 输出契约

| 项 | 值 | 来源 |
|:---|:---|:---|
| 输入 x1/x2 | FLOAT16、BFLOAT16 | 赛题 3.3 |
| 输出 y | FLOAT32，shape `(B,)` | 赛题 3.6 |
| 精度 | fp32 相对/绝对误差 < 1e-4 | 赛题 五 |

### 2.2 存储布局定义

```
transposeX1 = false  →  x1 物理布局 (B, M, K)
transposeX1 = true   →  x1 物理布局 (B, K, M)
transposeX2 = false  →  x2 物理布局 (B, K, N)
transposeX2 = true   →  x2 物理布局 (B, N, K)
逻辑形状恒为 x1:(B,M,K)、x2:(B,K,N)
```

**证据**：平台自带的 `scripts/BatchMatmulMaxSum.py`：

```python
def _physical_shapes(B, M, N, K, transposeX1, transposeX2):
    x1_shape = (B, K, M) if transposeX1 else (B, M, K)
    x2_shape = (B, N, K) if transposeX2 else (B, K, N)
    return x1_shape, x2_shape
```

`gen_data.py` 用这个函数生成实际写入 `.bin` 的数组，`main.asc` 再把同一形状
填进 `TensorGroupInfo`。**数据文件的物理布局已确定。**

### 2.3 Ascend C 执行空间规则

> `__aicore__` 修饰的函数只能在 Device 侧执行，**只能被 `__global__` 或其他
> `__aicore__` 函数调用**。无限定符定义的函数**默认是 host 函数**。

**来源**：CANN《函数执行空间限定符》表 1

**教训**：曾把一个 `__aicore__ inline constexpr` 的辅助函数同时用在 kernel 和
host 两侧，导致 **15/15 Compile Error**。跨 host/device 的公共函数一律不要抽。

### 2.4 UB 流水同步必须手动插入

官方《关键特性说明》：

- **表 3**（开启 `cce-auto-sync`，AIV）：`MTE2→V` 与 `V→MTE2` 均标为 `-`，**不自动插入**
- **表 1**（TPipe-TQue 框架）：这两个方向标为「支持」，**但使用约束要求
  「正确使用 EnQue/DeQue、AllocTensor/FreeTensor 接口」**
- 本 kernel 用的是裸 `TBuf` + `pipe.InitBuffer` + 直接 `DataCopyPad`/`WholeReduceMax`，
  **没有 TQue、没有 AllocTensor/EnQue/DeQue** ⇒ 自动同步不生效

**官方反例 2 与本 kernel 结构逐行同构**，且原文明确说这会导致「样例执行失败」。

**修复**（已用于版本 D）：

```cpp
// DataCopyPad 循环之后
AscendC::SetFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
AscendC::WaitFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
// colChunks 循环之后
AscendC::SetFlag<AscendC::HardEvent::V_MTE2>(EVENT_ID1);
AscendC::WaitFlag<AscendC::HardEvent::V_MTE2>(EVENT_ID1);
```

**注意**：`SetFlag`/`WaitFlag` 必须成对且参数一致，否则 timeout 卡死；
**不要用 `EVENT_ID6`/`EVENT_ID7`**（6 系统预留，7 被 TPipe 自动同步占用）。

### 2.5 评测用例比赛题正文宽松

赛题 3.4 节写 `32 ≤ K ≤ 8192` 且 K 为 8 的倍数，
但模板 `scripts/BatchMatmulMaxSum.py` 保留的 case 1 是：

```python
( 1,   1,  2,   3,  4, "float16",  False, False, ...)
#     B=1  M=2  N=3  K=4        ← K=4
```

**K=4 既不 ≥32 也不是 8 的倍数。** 不能假设评测用例遵守赛题的维度约束。

## 三、尚未解决的问题

### 3.1 【核心悬案】`TensorGroupInfo.shape` 是存储形状还是逻辑形状？

**两件事互相独立**，不能混为一谈：

- ✅ 已确定：**`.bin` 数据文件按物理布局存放**
- ❓ 未知：**`TensorGroupInfo.shape` 里报的是哪一种**

两种解释下的正确读法：

| | 若 shape = 逻辑形状 | 若 shape = 存储形状 |
|:---|:---|:---|
| x1 的 M | `shape[1]` | `shape[transposeX1 ? 2 : 1]` |
| x1 的 K | `shape[2]` | `shape[transposeX1 ? 1 : 2]` |
| x2 的 N | `shape[2]` | `shape[transposeX2 ? 1 : 2]` |

**现有证据相互矛盾**：

| 实验 | 结果 | 指向 |
|:---|:---|:---|
| 版本 B（按"存储形状"改 x1） | 0 通过 | 逻辑形状 |
| 版本 C（按"逻辑形状"改 x2） | 3 通过（在 A 的噪声带内） | 无结论 |

**未被验证的可能**：版本 B 那次编辑可能有误（虽然报的是 Wrong Answer 而非 Compile Error）。

**一锤定音的办法**：拿到定义 15 个用例的 `npu_cases` JSON，或做一次干净的、
只改一行的对照实验，并**重复提交两次**排除噪声。

### 3.2 残余非确定性

版本 D 两次提交为 7、8，**仍有 ±1 波动**（相比版本 A 的 3~5 已大幅收敛）。

**待查方向**：`cGm` 在 `mb` 循环之间被复用 —— 上一次 M 块的
`DataCopyPad`（MTE2 读 `cGm`）与下一次 `mm.IterateAll`（FIX 写 `cGm`）
之间存在 WAR 冒险。官方表 2 中 `FIX→MTE2` 标为"暂无应用场景"，配对方式待确认。

### 3.3 剩余失败点

版本 D 的 7 通过那次的失败点分布：

| 测试点 | 错误占比 | 推测性质 |
|:---|:---|:---|
| 2, 4, 7, 8, 11, 12, 15 | **100.00%** | 结构性错误 —— 可能是变体标志（transpose / bf16）处理错 |
| **5** | **12.50%** | **部分错误** —— 形状解析是对的，是某个 batch 的边界问题 |

**12.50% = 1/8**。若测试点 5 的 `B=8`，即"8 个输出里恰好 1 个错"，
指向多核分配逻辑 `for (b = GetBlockIdx(); b < B; b += coreNum)`。

**注意**：点 2 是"全负相似度"专项测试（模板里有 `assert np.all(y < 0)`），
它 100% 错误，说明 MaxSim 初值 / 尾块 padding 那条线可能有问题。

## 四、关键常量与设计决策

| 常量 | 值 | 含义 / 约束 |
|:---|:---|:---|
| `kBaseM` | 64 | 单核处理的 M 行数，须与 host 侧 `SetShape` 一致 |
| `kTileN` | 256 | 归约的列块宽度，须为 64 的倍数 |
| `kF32PerRepeat` | 64 | 一个 repeat 的 fp32 元素数（256B） |
| `kSlackElems` | 8 | scratch 尾部余量 |
| `kNegBig` | `-3.0e38f` | 代替 -inf，避免与 NaN 交互 |
| `kReduceStride` | 2 | `WholeReduceMax` 默认 `ORDER_VALUE_INDEX`，产出 `[value,index]` 交错 |

**并行策略**：按 B 切分，每核处理完整的 batch，核内固定顺序累加（保证确定性）。
`blockNum = min(B, availableCoreNum)`。

**已知性能缺陷**：B 较小时大量核空转（B=1 只有 1 个核工作）。
赛题明确要求「沿 B 维**和/或 M 维**合理分配多核任务，兼顾**较小 Batch**」。
改造需引入跨核归约，会破坏当前的确定性保证 —— 但可用「两阶段 + SyncAll」兼顾。

## 六、下一步建议

### 优先级 1：确认版本 D 的稳定性

**原封不动再提交 1~2 次**，看通过数是否稳定在 7~8、通过点是否一致。

- 稳定 → 竞态已收敛，可以放心做后续优化
- 仍抖动 → 继续查 3.2 的 `cGm` 复用冒险

**判据不是「通过数变多」，而是「多次执行结果一致」。**

### 优先级 2：拿到 `npu_cases` JSON

这是解开 3.1 悬案、精确定位剩余 7~8 个失败点的最短路径。
**寻找位置**：赛题页面附件、答题界面下载项、工程目录中的 `.json` 文件。

### 优先级 3：按错误占比分类进攻

- **12.5% 的点 5** → 多核分配 / 边界
- **100% 的点 2** → 全负相似度专项（MaxSim 初值、尾块 padding）
- **100% 的其他点** → 变体标志（transpose / bf16）

### 优先级 4（性能，最后做）

多核利用率：B 小时沿 M 维切分。用「阶段一各核写 partial + SyncAll + 阶段二固定
顺序求和」保持确定性。赛题性能基线是拆分实现，当前实现还很慢
（点 13 最优 1.40µs，本实现 549µs）。
